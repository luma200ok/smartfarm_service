## 1. 개요 (Overview)

토마토 잎 사진을 올리면 **AI가 병해를 진단**하고, 그 진단 결과를 근거로 **LLM이 자연어 처방**을 생성해 주는 **농장 단위 멀티테넌시 웹 서비스**. 기존 솔로 AI 프로젝트 `smartfarm_ai`(ML/DL/LLM)의 추론 능력을 **여러 사람이 농장을 공유하며 쓰는 3-tier 서비스**로 확장한 것이 본 프로젝트다.

### 1.1 배경 및 문제 정의

- 스마트팜 센서는 **온습도·EC 같은 "환경 숫자"만** 보여준다. 정작 재배자가 알고 싶은 것은 "지금 이 잎이 병든 건가", "그럼 뭘 해야 하나"인데, 이 판단은 여전히 사람의 경험에 의존한다.
- 잎 병해 판독은 숙련도 편차가 크고, **진단 결과가 개인 기기에만 남아** 농장 단위로 축적되지 않는다. 같은 농장을 여러 명이 관리해도 "누가 언제 무엇을 진단했는지"가 공유되지 않는다.
- 선행 프로젝트 `smartfarm_ai`는 진단·처방 모델을 **Streamlit 단일 데모**로 검증했다. 모델은 동작하지만 **계정·농장·이력·권한이 없어** 실제 농가 팀이 쓸 수 없다 — 이 간극이 본 서비스의 존재 이유다.

### 1.2 솔루션 요약

1. 이메일 회원가입 + **JWT 인증**(access 30분 / refresh 14일, 로테이션·재사용 감지)
2. **농장(Farm) = 테넌트** 생성, **초대코드**로 팀원 합류 — OWNER/MEMBER 2단계 권한
3. 잎 사진 업로드 → **동기 진단**(CNN 4분류 + Grad-CAM 오버레이 + 2단 OOD 게이트) → 농장 이력에 적재
4. 진단 결과를 근거로 **LLM 처방 요청** → 비동기 job(202 접수 → 폴링) → 구조화 처방(요약·조치·주의·출처)
5. 농장별 **진단·처방 이력**을 팀원 전원이 공유 조회

### 1.3 기존 `smartfarm_ai`와의 관계

| 구분 | `smartfarm_ai` (기존 솔로 레포) | `smartfarm_service` (본 프로젝트) |
|---|---|---|
| 성격 | ML/DL/LLM 실험·모델 서빙 | 멀티테넌시 웹 서비스 |
| 산출물 | 학습 파이프라인, FastAPI 추론 서버, Streamlit 데모 | Spring Boot backend + Next.js frontend |
| 본 프로젝트에서의 취급 | **1차 범위에서 코드 무변경** — `smartfarm-api.service`(FastAPI :8000)를 **내부 호출로 재사용** | ai-server를 외부에 노출하지 않고 backend가 프록시 |
| 모델 실측(원본 레포 README 기준) | 잎 진단 4분류 ResNet18 **acc 0.96 / ROC-AUC 0.997**, YOLOv8n **mAP@50 0.78**, 부위 분류기 **acc 0.932**, 식물 게이트 `plant_score < 0.04` | 이 수치를 **서비스가 그대로 승계**(재학습·재캘리브레이션 없음) |

> 즉 본 프로젝트의 제품 가치는 "더 좋은 모델"이 아니라 **"모델을 팀이 쓸 수 있게 만든 것"** 이다. AI 성능 개선은 원본 레포의 과제로 분리한다.

## 2. 목표 (Goals)

### 2.1 프로젝트 목표

- 회원가입 → 농장 생성 → 팀원 초대 → 잎 사진 진단 → LLM 처방까지 **E2E 흐름을 실제 도메인(HTTPS)에서 무결점 완주** — ✅ 달성(2026-08-20, `farm.luma200ok.com` 외부 스모크 통과 — DNS·certbot 완료 직후)
- **cross-tenant 데이터 격리 100%** — 농장 ID는 입력값으로 취급하고 매 요청 멤버십을 재검증 (IDOR 전수 테스트 통과, PR #12)
- 16GB 단일 ARM 서버에서 **LLM·AI·DB·백엔드·프론트를 전부 자가호스팅**하고 메모리 피크 안에서 안정 가동
- 외부 유료 API **의존 0** — LLM은 로컬 Ollama, 인증은 자체 JWT

### 2.2 목표 사용자 (Persona)

| 페르소나 | 설명 | 핵심 니즈 |
|---|---|---|
| 농장주 (OWNER) | 농장을 개설하고 팀원을 초대·관리 | 농장 단위로 진단 이력을 모으고, 누가 들어와 있는지 통제 |
| 재배 담당자 (MEMBER) | 현장에서 잎을 찍고 조치하는 사람 | 사진 한 장으로 즉시 병해 판단 + "지금 뭘 해야 하나" 답 |
| 신규 재배자 | 경험이 적어 병징 판독이 어려움 | 판단 근거(Grad-CAM)와 처방 출처가 함께 보이는 설명 |
| 운영자(개발자 본인) | 단일 서버 운영 | 리소스 초과 없이 안정 가동, 장애 시 원인 추적 |

### 2.3 범위 정의

**In-Scope (P0 — 구현 완료)**

- 이메일/비밀번호 회원가입·로그인, JWT access/refresh, refresh 로테이션 및 **재사용 감지 시 전체 무효화** (FR-1)
- 농장 CRUD(soft delete) + 멤버 목록·제거·자발 탈퇴 (FR-2)
- **초대코드 합류** — OWNER 발급, 만료 72h, 농장당 활성 코드 1건, DB에는 SHA-256 해시만 저장 (FR-2)
- 잎 사진 **동기 진단** 프록시 + 결과 이력화 + Grad-CAM 오버레이 보관 (FR-3·FR-4)
- **LLM 처방 비동기 job** — 202 접수 → 단일 워커 직렬 처리 → 폴링 조회, 농장당 진행 중 3건 상한 (FR-5·FR-6)
- 프론트: 인증 화면, 농장 목록·상세, 진단 업로드·이력·상세, 처방 요청·폴링·이력
- 운영: HTTPS 도메인, GitHub Actions CI/CD(jar 백업·심링크 스왑·헬스체크), systemd 네이티브 배포

**P1 — 다음 우선순위 (미구현)** — 우선순위 스냅샷은 `STATUS.md` "다음 플랜 후보"(2026-08-20, 결정 대기)와 이슈 #9(umbrella)를 따른다

- **FE 마감 한 묶음**: ① **ErrorCode `P004` 반영** — 백엔드는 P004(처방 대기 한도 초과, 429)를 반환하는데 `frontend/src/constants/index.ts` 메시지 맵에 **P004가 없어** 기본 메시지로 폴백된다(실측) ② **처방 `caution` 렌더 정합** — 본문이 자체 라벨을 포함하므로 "주의사항" 헤딩을 덧붙이지 않는다, `actions`는 즉시조치+예방 통합 리스트 ③ `FarmDetail` getMe 분리
- **refresh_tokens 만료분 퍼지 스케줄러** — 만료 토큰이 테이블에 무한 적재됨(리뷰 P2-6, 후속 분리)
- **ArchUnit 가드 규칙** — farm 스코프 서비스가 `FarmAccessGuard`에 의존하도록 강제. 다음 farm-scoped 기능 착수 전 안전망(테넌시 누락을 컴파일 단계에서 잡기 위함)
- **환경 대시보드**(FR-7) — 원본 레포 '오늘 운영'(외기·제어 후 내부값·장치 상태)을 서비스에 노출. **ai-server 조회 엔드포인트 추가가 필요 = "1차 ai-server 무변경" 원칙의 첫 해제 지점**이라 범위 협의 필수
- **회원 탈퇴** — soft delete + `revokeAllByUserId` 동반(보안 리뷰 P2-3이 완료 조건으로 지정) + `farm_members` 유령 멤버십 정리
- **알림** — 경보·처방 완료 디스코드 웹훅(원본 레포 notify 재활용)
- 진단 **이미지 원본 저장** 및 재열람 (`imageUrl`) — 1차는 결과만 이력화

**P2 — 확장 목표 (Stretch)**

- **작물 확장** — 현재 `CropType`은 `TOMATO` 단일(ai-server 모델 제약). 딸기·오이 등은 원본 레포 전이학습 결과가 서빙에 반영돼야 가능
- 환경 시계열 예측(LSTM)·규칙 기반 자동 관제의 서비스 이식
- 역할 3단계(`MANAGER` 추가), 농장 간 데이터 비교
- 모바일 대응 촬영 UX(현장 촬영 → 즉시 업로드)
- **운영 안정화**(STATUS 후보 P2): PG 백업 cron(`pg_dump smartfarm_service`) · certbot 자동갱신 cron에 farm 도메인 포함 확인 · `processing_started_at`(V5)·`@Lob` 제거 등 #9 구조 개선 잔여 · README 아키텍처 다이어그램·라이브 링크

**Out-of-Scope**

- **AI 모델 학습·재학습** — 원본 `smartfarm_ai` 레포 소관. 본 레포는 추론 결과의 소비자다
- **결제·요금제** — 과금 로직 일절 없음 (§2.4)
- **스케일아웃** — backend는 **단일 인스턴스 전제**. 처방 워커의 복구·픽업이 인스턴스를 구분하지 않아 다중 인스턴스 시 중복 처리가 발생한다(§10, §11-2)
- 법적 효력을 갖는 방제 처방 — 본 서비스는 **재배 판단 보조 도구**이며 농약 사용은 사용자 책임

### 2.4 비즈니스 모델 (가설 — 현재 미구현)

현재 서비스에 **플랜·쿼터·결제 코드는 존재하지 않는다**(요금 관련 테이블·API 0건 — 실측). 아래는 확장 시의 가설이며, 착수 전 §11에서 확정해야 한다.

| 가설 축 | 내용 |
|---|---|
| 과금 축 후보 | 농장 수 · 월 진단 장수 · 팀원 좌석 수 — 실원가(GPU 없는 ARM CPU 추론 시간, LLM 점유 시간)와 비례하는 축은 **처방 요청 수**가 가장 유력 |
| 원가 구조 | 외부 API 비용 0(자가호스팅), 실질 원가 = **단일 서버 자원**. 특히 처방 1건이 LLM을 ~16초 독점하므로 동시 사용자 증가 = 대기시간 증가로 직결 |
| 무료/유료 분기 후보 | 진단(1~2초, 가벼움)은 전 사용자 / **처방(LLM 점유)은 한도제** — 현재 구현된 "농장당 진행 중 3건 상한"이 이미 사실상의 쿼터 뼈대 |
| 선결 조건 | 스케일아웃 불가 상태(§11-2)에서 유료화는 불가. 워커 소유권·다중 인스턴스 대응이 선행돼야 한다 |

## 3. 유사 서비스 벤치마킹

| 서비스 | 구분 | 참고 포인트 |
|---|---|---|
| Plantix | 해외(농민용 앱) | 사진 1장 → 병해 진단 → 방제 처방까지의 **단일 흐름 UX**. 본 서비스의 진단→처방 동선이 같은 패턴 |
| 농사로/스마트팜코리아 | 국내 공공 | 작물별 재배·병해 표준 정보 — RAG 근거 출처의 성격이 유사(원본 레포 RAG 컬렉션) |
| 그린랩스 팜모닝 | 국내 | 농장 단위 관리 + 팀 공유. **농장을 조직 단위로 두는 모델**의 근거 |
| 기존 센서 관제 솔루션(일반) | 국내 | 환경 수치 모니터링에 특화 — 본 서비스는 여기에 **"그래서 뭘 하라"는 처방**을 얹는 것이 차별점 |

공통 패턴: **계정 → 농장(자산) → 촬영/센싱 → 진단 → 조치 가이드 → 이력 축적**. 본 서비스의 IA도 이 흐름을 따른다.

## 4. 메뉴 구성 (IA)

실제 라우트 기준(`frontend/src/app/**` 실측).

```
🔐 (auth) — 비로그인 영역
 ├ /login          로그인 (LoginForm)
 └ /signup         회원가입 (SignupForm → 성공 배너 → 로그인 유도)

📊 (dashboard) — 인증 필요 영역
 ├ /dashboard                                   대시보드 홈 — 내 농장 요약 카드
 │    └ 농장 0개면 "농장 만들기 / 초대코드로 합류" 유도
 ├ /farms                                       농장 목록 + 농장 생성 폼
 ├ /farms/[farmId]                              농장 상세 — 정보·멤버·진단/처방 진입
 ├ /farms/[farmId]/diagnoses                    진단 — 사진 업로드 + 이력 목록(페이지네이션)
 ├ /farms/[farmId]/diagnoses/[diagnosisId]      진단 상세 — 라벨·확률·부위·Grad-CAM 오버레이
 ├ /farms/[farmId]/prescriptions                처방 — 질문 작성(진단 연결 선택) + 이력 목록
 ├ /farms/[farmId]/prescriptions/[id]           처방 상세 — 상태 폴링 → 결과(요약·조치·주의·출처)
 └ /invitations                                 초대코드 입력 → 농장 합류
```

- 전역 헤더: 서비스명 + 로그아웃 (`DashboardHeader`, `LogoutButton`)
- **관리자 콘솔 없음** — 플랫폼 운영자 화면은 범위 밖(운영은 서버 직접 접근)
- 랜딩 페이지: `/`는 현재 **소개 페이지가 아니라 진입 리다이렉트 성격** — 마케팅 랜딩은 미구현

## 5. 핵심 기능 요구사항

> 표기 규칙: 각 FR은 **현재 코드가 하는 일**을 기술한다. 계획·희망은 `(미구현)`으로 명시한다.
> 스펙 세부(요청/응답 필드)는 중복 기술하지 않고 [`api-contract.md`](../api-contract.md) 해당 절을 참조한다.

### FR-1 회원가입 · JWT 인증 (contract §1)

- 이메일/비밀번호(8자 이상)/닉네임(2~20자) 가입. 이메일은 서버에서 `trim().toLowerCase()` **정규화 후 저장·비교** — 대소문자 무관 단일 계정
- 토큰: **access 30분 + refresh 14일**. refresh는 **DB 저장 + 로테이션**, **재사용 감지 시 해당 사용자의 refresh 전체 무효화**
- **401 코드 분리가 계약의 핵심**: `A003` = access 만료(**refresh로 회복 가능한 유일한 401**) / `A004` = 토큰 무효·변조·재사용·refresh 만료(재로그인). 클라이언트는 **A003에만 refresh를 재시도**한다
- **클라이언트 refresh는 single-flight 의무** — 동시 401이 여러 건 발생해도 refresh 요청은 1건만 발화하고 나머지는 그 결과를 공유한다. 로테이션 토큰은 1회성이라 병렬 refresh가 **재사용 감지 오탐**을 유발하기 때문. `frontend/src/lib/api/auth.ts`의 in-flight Promise로 구현
- 프론트 저장 키는 앱 prefix 고정: `localStorage['farmAccessToken']` / `['farmRefreshToken']`
- **수용된 트레이드오프**: 로그아웃·전체 무효화 이후에도 이미 발급된 access 토큰은 stateless 특성상 **최대 30분 유효**하다
- **미구현**: 이메일 인증, 비밀번호 찾기·재설정, 소셜 로그인, 회원 탈퇴

### FR-2 농장(테넌트) 관리 · 초대 멤버십 (contract §2)

- **테넌트 = Farm**, 식별자는 path param `{farmId}`. **입력값으로 취급하고 매 요청 멤버십을 재검증**한다(`FarmAccessGuard.requireMember/requireOwner`) — cross-tenant IDOR 차단. repository 조회는 **항상 farm 스코프**(`findByIdAndFarmId` 형태)
- 역할 2단계: `OWNER`(농장 수정·삭제·초대 발급·멤버 제거) / `MEMBER`(조회·진단·처방). `MANAGER`는 후속
- 농장 생성자는 자동 OWNER. 농장 삭제는 **soft delete**
- **초대코드 정책**(2026-08-19 확정):
  - OWNER 발급, **만료 72시간**, 만료 전까지 **다인 재사용 가능**
  - **농장당 활성 코드 1건** — 재발급 시 기존 코드 즉시 무효화
  - **멤버 제거·자발 탈퇴 시 해당 농장의 활성 코드 자동 무효화** — 제거된 멤버가 들고 있던 코드로 재합류하는 경로를 끊기 위함
  - 코드는 **DB에 SHA-256 해시로만 저장**(평문 미보관), 무효·만료는 `F004`
- **OWNER 본인 탈퇴 불가**(`F006`) — 농장 삭제로만 가능. 농장이 주인 없는 상태가 되는 것을 막는다
- 이미 멤버인 사용자의 재합류는 `F005`

### FR-3 잎 병해 진단 (contract §3 · ai-server 연동)

- 입력: multipart `file` 1장. 서버 검증 **10MB 이하 + `image/*` content-type** — 빈 파일/초과/비이미지는 **전부 `D002`로 통일**(응답 일관성 우선)
- 처리: backend가 ai-server `POST /api/diagnoses`를 **동기 호출**(~1-2초) → 결과를 `diagnoses` 테이블에 적재 → 201 반환
- **트랜잭션 밖 호출 강제**(`@Transactional(propagation = NOT_SUPPORTED)`) — 외부 호출을 트랜잭션 안에서 하면 최대 30초 동안 Hikari 커넥션을 물고 있어 **풀 고갈로 무관한 엔드포인트까지 마비**된다. 리뷰에서 P1으로 잡혀 수정된 실제 사고 패턴(PR #13)
- **2단 OOD 게이트**(ai-server 소관): 식물 여부(`plant_score`) + 부위 분류기로 과육·비잎 입력을 걸러낸다. 차단 시 ai-server도 **200을 반환**하며 backend는 이를 `status = ood_blocked`로 저장한다 — 오류가 아니라 **정상적인 "판단 불가" 결과**로 취급
- 결과 필드: `label`·`labelKr`(4분류: 정상/잎곰팡이병/황화잎말이/잎마름역병)·`prob`·`part`·`reason?`·`camPngBase64`(Grad-CAM 오버레이)
- **이미지 원본은 저장하지 않는다** — 디스크·개인정보 부담 최소화. 보관하는 것은 **결과와 Grad-CAM 오버레이뿐**(`V3__diagnoses.sql` 주석 명시). `imageUrl`은 스키마상 자리만 있고 미구현
- ai-server 장애·비정상 응답은 `D003`(502)

### FR-4 진단 이력 (contract §3·§4)

- 농장 스코프 목록 조회(`?page&size`) — 최신순. 인덱스 `(farm_id, created_at DESC, id DESC)`로 **동시각 tie-break까지 안정 정렬**
- 목록 DTO(`DiagnosisSummaryResponse`)는 **무거운 필드(base64 오버레이)를 제외**한다 — 목록에서 이미지 payload를 실어 나르지 않기 위한 의도적 분리
- 상세 조회는 `findByIdAndFarmId` — **다른 농장의 진단 ID를 넣어도 404(`D001`)** 로 떨어진다(존재 여부 자체를 노출하지 않음)
- 페이지 크기는 전역 `max-page-size: 100`으로 상한(과대 페이지 요청 방어)
- 응답은 Spring `Page`를 직접 노출하지 않고 **`PageResponse<T>` record로 매핑**(직렬화 포맷 고정)

### FR-5 LLM 처방 비동기 job (contract §3)

제품적으로 가장 까다로운 기능. **LLM 1건이 서버 자원을 ~16초 독점**하기 때문에 동기 요청으로는 서비스가 성립하지 않는다.

- **접수**: `POST` 시 `PENDING`으로 저장하고 **즉시 202** 반환. 질문 1~500자, 진단 연결(`diagnosisId`)은 선택
- **처리**: backend 내 **단일 스레드 executor**가 순차 처리(`PROCESSING`) → ai-server `POST /api/prescriptions` 호출(동기 ~16초, 서버 동시성 캡 2) → `COMPLETED`/`FAILED`
- **상태머신**: `PENDING → PROCESSING → COMPLETED | FAILED`
- **혼잡 대응**: ai-server 429 시 **백오프 재시도 2회(5s·15s)** 후 실패. 소진 시 `P003`, 그 외 생성 실패는 `P002`
- **접수 상한**(2026-08-19 확정): 농장당 진행 중(PENDING+PROCESSING) **3건 초과 시 `P004`(429)**. 워커 큐도 유한 — 포화 시 **저장조차 하지 않고** P004. 재기동 복구 재큐잉에도 상한·연령 컷오프를 적용해 초과분은 `P002 FAILED` 처리
- **재기동 복구**: `PrescriptionRecoveryInitializer`가 기동 시 비종료 상태를 스캔해 재큐잉. 스캔 비용이 잔존 건 수에만 비례하도록 **partial index**(`status IN ('PENDING','PROCESSING')`)를 둔다
- **응답 매핑**: ai-server의 처방 응답은 **한글 키 스키마**(`진단요약·원인·즉시조치·예방·재촬영시점·근거출처`)다. backend가 영문 result 스키마(`summary`/`actions[]`/`caution`/`sources[]`)로 매핑하며, **필수 필드(`summary`)가 null·blank면 `P002 FAILED`** — 빈 성공을 금지한다. 필드별 크기 캡 적용
- **수용된 트레이드오프**: ai-server가 LLM 실패 시에도 200 + 실패 안내문을 줄 수 있다. 이 경우는 `COMPLETED`로 수용한다(2026-08-19 확정)

### FR-6 처방 이력 · 폴링 (contract §3)

- 상세 조회 API를 **폴링 엔드포인트로 겸용** — 프론트 `PrescriptionPoller`가 2~3초 간격으로 상태를 확인한다(SSE·WebSocket 미도입)
- **`FAILED`는 반드시 `errorCode`를 동반**한다. 프론트는 `P003`이면 "잠시 후 재시도" 유도를, `P002`면 실패 안내를 렌더한다 — 실패 사유에 따라 사용자 행동이 갈리기 때문
- 목록 DTO는 `result` 본문을 제외(FR-4와 동일 원칙)
- **실측 결함**: `P004`가 FE `ERROR_MESSAGES` 맵에 없어 한도 초과 시 기본 메시지로 폴백된다 → §2.3 P1 항목

### FR-7 환경 대시보드 (P1 — **미구현**)

- 목표: 오늘의 온습도·경보 등 **운영 데이터**를 농장 화면에 표시. 원본 `smartfarm_ai`에 규칙 기반 관제·자동 경보 로직이 이미 있다
- **현재 상태: 범위 미정.** 노출 대상은 원본 레포의 '오늘 운영'(KMA 외기 · 제어 후 내부값 · 장치 상태)이나, 이를 서비스가 읽으려면 **ai-server에 조회 엔드포인트 추가가 필요**하다 — **"1차 ai-server 무변경" 원칙의 첫 해제 지점**
- 착수 전 확정 필요: 원칙 해제 여부 · 데이터 소스 · 테넌트 귀속 방식(농장↔센서 매핑) · 갱신 주기 — §11-5

## 6. 시스템 아키텍처

```
브라우저 ── https://farm.luma200ok.com (Cloudflare Proxied → arm1 nginx, certbot TLS)
              ├─ /            → Next.js standalone (127.0.0.1:3000, systemd)
              └─ /api         → Spring Boot (127.0.0.1:8085, systemd, -Xmx512m)
                                  ├─ PostgreSQL 16 (native, DB: smartfarm_service)
                                  └─ ai-server (127.0.0.1:8000, 외부 비노출)
                                        └─ 로컬 Ollama (qwen2.5:7b · exaone3.5:2.4b · bge-m3)
```

- **레포 분리**: 본 레포 = `backend/` + `frontend/` + `docs/`. ai-server는 `smartfarm_ai` 레포 유지(1차 무변경)
- **외부 의존 없음**: LLM·AI·DB 전부 자가호스팅. 유료 API 키 0건
- backend·ai-server는 **127.0.0.1 바인딩** — nginx 경유만 허용. `forward-headers-strategy: framework`로 TLS 종단 뒤 스킴 정합

### 6.1 배포 환경 — oci-arm1 (도커 미사용, 전부 네이티브 systemd)

| 항목 | 값 | 비고 |
|---|---|---|
| 서버 | oci-arm1 (3코어 / **16GB**) | 단일 VM 올인 |
| backend | Spring Boot 3.x · Java 21 · `-Xmx512m` | Flyway V1~V4 적용 |
| frontend | Next.js standalone · Node 22 | **서버에서 빌드 금지** — GH Actions가 빌드해 산출물만 배포 |
| DB | 네이티브 PostgreSQL 16, DB `smartfarm_service` | 같은 서버의 타 프로젝트 DB와 분리 |
| 시크릿 | `/etc/app-secrets/smartfarm-service.env` (root:600) | DB 비번·JWT_SECRET·프로필 등 7키. 레포에 평문 없음 |
| CI/CD | GitHub Actions — PR CI + main 배포(jar 백업 → 심링크 스왑 → 헬스체크) | green 실측 |

**⚠️ 자원 전제 (제품 제약으로 직결)**

- **LLM 로드 피크 12~14GB / 16GB.** 여유가 2~4GB뿐이라 처방을 병렬 처리할 수 없다 → FR-5의 단일 워커 직렬화는 **설계 취향이 아니라 자원 제약의 결과**다
- **Next 빌드는 절대 서버에서 하지 않는다**(빌드 메모리가 LLM과 충돌)
- **backend 단일 인스턴스 전제.** 처방 워커의 복구·픽업이 인스턴스를 구분하지 않아 스케일아웃 시 **같은 job을 여러 인스턴스가 집는다**. 스케일아웃하려면 owner/heartbeat 컬럼이 선행 필요 → §11-2

### 6.2 데이터 모델 (Flyway V1~V4 실측)

```
users ──< refresh_tokens
  │
  └──< farm_members >── farms ──< invitations
                          │
                          ├──< diagnoses ──┐
                          └──< prescriptions (diagnosis_id FK, nullable)
```

| 테이블 | 마이그레이션 | 핵심 포인트 |
|---|---|---|
| `users` / `refresh_tokens` | V1 | refresh는 **해시 저장 + 로테이션**. 만료분 퍼지 스케줄러 **미구현**(P1) |
| `farms` / `farm_members` / `invitations` | V2 | 초대코드 **SHA-256 해시만** 저장. 농장 soft delete |
| `diagnoses` | V3 | **원본 이미지 미저장**, `cam_png_base64`만 보관. `(farm_id, created_at DESC, id DESC)` 인덱스 |
| `prescriptions` | V4 | `result JSONB`(구조화 처방), `error_code`. 비종료 상태 **partial index**로 복구 스캔 비용 억제 |

- 시각 필드는 전부 **서버 로컬(Asia/Seoul) naive datetime** — 레포 공통 규칙
- Flyway 규칙: `V{n}__{설명}.sql`, **기존 마이그레이션 수정 금지**, `out-of-order=true`

### 6.3 개발 컨벤션

- **Entity**: `@Getter`만(Setter 금지), `@NoArgsConstructor(PROTECTED)` + `@Builder`, 상태 전이는 엔티티 메서드로 캡슐화
- **DTO**: Request/Response 전부 **record**, 엔티티 직접 노출 금지, Response는 `from(Entity)`
- **Service**: 클래스 `@Transactional(readOnly=true)`, 쓰기만 명시. 예외는 **`CustomException(ErrorCode)` 단일 패턴** → `GlobalExceptionHandler` 일괄 → `{timestamp, code, message}`
- **Controller**: `ResponseEntity<DTO>` + `@Valid`, 비즈니스 로직 금지
- **ErrorCode 체계**(contract §5): 도메인 prefix + 3자리 — `C`(공통)/`A`(인증)/`F`(농장)/`D`(진단)/`P`(처방). 프론트는 **메시지 문자열이 아니라 code로 분기**한다
- 프론트: URL 하드코딩 금지(`NEXT_PUBLIC_API_URL` 미설정 시 프로덕션 빌드 실패), API 래퍼는 `lib/api/{도메인}.ts`, 에러는 `.status`/code로 분기

## 11. 오픈 이슈 (확정 필요)

1. **ai-server 처방 질문 보존 정책** — ai-server가 처방 질문 원문을 farm/user 구분 없이 자체 DB(`src/llm/history.py`)에 혼합 저장한다. 서비스 오픈 전 검토 항목이었으나 **미해결 상태로 오픈됐다**. 비활성화 / 익명화 / 테넌시 태깅 중 택일 필요 — 개인정보·테넌시 경계 양쪽에 걸린 사안이라 우선순위 상위
2. **스케일아웃 전제 조건** — 처방 워커의 복구·픽업에 **인스턴스 소유권(owner) + heartbeat**가 없다. 다중 인스턴스 시 같은 job 중복 처리. 유료화·트래픽 증가 시 **선행 필수**
3. **ai-server 계약 테스트 부재** — backend는 ai-server의 한글 키 응답 스키마에 강결합돼 있는데, 원본 레포 변경을 감지할 **크로스 레포 계약 테스트가 없다**. 원본이 필드명을 바꾸면 운영에서야 P002로 드러난다. 골든 응답 픽스처 기반 계약 테스트 도입 여부 확정 필요
4. **백업·복구 정책** — 단일 VM에 DB가 상주하는데 **백업이 구성돼 있지 않다**. `pg_dump` cron이 STATUS 후보 P2로 등재됐을 뿐 실행 전이며, 보관 주기·복구 리허설도 미정. 오픈된 서비스에 실사용 데이터가 쌓이기 시작하면 **가장 먼저 갚아야 할 부채**
5. **환경 대시보드(FR-7) 범위 — ai-server 무변경 원칙의 해제 여부** — 원본 레포의 '오늘 운영' 데이터를 노출하려면 **ai-server에 조회 엔드포인트를 추가해야 한다**. 이는 본 프로젝트가 지켜온 "1차 ai-server 코드 무변경" 원칙의 **첫 해제 지점**이므로, 데이터 소스·농장↔센서 매핑·갱신 주기와 함께 **원칙 해제 자체를 먼저 결정**해야 한다. contract 갱신 선행
6. **작물 확장 트리거** — `CropType` enum 확장은 준비됐으나 실제 확장 조건(원본 레포 전이학습 모델의 서빙 반영 시점, 작물별 4분류 라벨 체계)이 미정
7. **비즈니스 모델 착수 여부**(§2.4) — 과금 축·플랜 설계 이전에 §11-2(스케일아웃)가 해소돼야 한다. 유료화를 실제로 할지 자체가 미확정
8. **관리자/운영 콘솔 필요성** — 현재 운영은 서버 직접 접근(수동 SQL)에만 의존한다. 계정 차단·농장 강제 삭제 등 **운영자 개입 경로가 코드에 없다**. 필요 시점·범위 확정 필요
9. **FE `P004` 메시지 누락** — 백엔드가 반환하는 P004가 프론트 ErrorCode 맵에 없어 기본 메시지로 폴백. 다음 FE 작업에 동승 처리 예정(사소하나 실사용 혼선 유발)
